# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev               # start dev server (http://localhost:3000), D1 emulated locally
npm run build              # plain `next build` (type-checks; does not deploy)
npm run preview            # build for Cloudflare + `wrangler dev` (real workerd runtime, local D1)
npm run deploy              # build for Cloudflare + deploy
npm run lint                # ESLint
npm run prisma:generate    # regenerate Prisma Client after editing prisma/schema.prisma
npm run db:migrate:local   # apply prisma/migrations SQL to local D1 (wrangler dev/next dev)
npm run db:migrate:remote  # apply prisma/migrations SQL to production D1
```

`db:migrate:local`/`db:migrate:remote` apply the `.sql` files under `migrations/` (wrangler's migration tracking, not Prisma's own `prisma migrate` workflow — D1 is applied via `wrangler d1 migrations apply`, Prisma is only used to author the schema and generate the client). After editing `prisma/schema.prisma`, generate the incremental SQL with `prisma migrate diff --from-url "file:./.wrangler/state/v3/d1/miniflare-D1DatabaseObject/<hash>.sqlite" --to-schema-datamodel prisma/schema.prisma --script` (find the hash via `find .wrangler -iname "*.sqlite"`), then `wrangler d1 migrations create vibehub <name>` and paste the SQL in. Prisma's generated SQLite `Json` defaults come out malformed (`DEFAULT []` instead of `DEFAULT '[]'`) — check generated SQL for this before applying.

**A Prisma-generated "RedefineTables" migration against D1 with existing data can silently cascade-delete child rows — confirmed by direct incident, not theoretical.** Adding `User.isAdmin` (migration `0006_add_admin_flag.sql`) should have been a trivial `ALTER TABLE "User" ADD COLUMN`, but Prisma's diff tool instead generated SQLite's drop-and-recreate pattern (`PRAGMA foreign_keys=OFF` → `CREATE new_User` → copy rows → `DROP TABLE "User"` → rename back). Applied against local/fresh D1 this is harmless, but applied via `wrangler d1 migrations apply --remote` against a database that already had real `ProjectMember` rows referencing `User` (`onDelete: Cascade`), it deleted every `ProjectMember` row in the database — D1 evidently did not honor the `foreign_keys=OFF` pragma for the whole statement batch, so the `DROP TABLE` cascaded for real. (Repaired after the fact via a one-off script re-creating the lost `OWNER` memberships from `Project`/`User` state — there was no automatic way to recover the exact prior data.) **Before writing a migration file, check whether the diff is a plain `ALTER TABLE ADD COLUMN` (safe) or a `RedefineTables`/drop-recreate (risky) — for the latter, manually rewrite it as a plain `ADD COLUMN` whenever the actual schema change is just adding a nullable/defaulted column, rather than pasting Prisma's generated SQL as-is.** If a genuine table rebuild is unavoidable on a database with real linked data, back up affected tables first (e.g. `wrangler d1 execute vibehub --remote --command "SELECT * FROM ProjectMember"` saved somewhere) before applying.

There is no test runner configured yet.

Local setup needs a `.env` (see `.env.example`) with `NEXTAUTH_SECRET` and `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`. `DATABASE_URL` in `.env` is a required-but-unused placeholder — Prisma's CLI needs the field to exist, but the real database is Cloudflare D1, accessed through a Workers binding, never through that URL. Production secrets are set via `wrangler secret put`, not `.env`.

## Architecture

VibeHub is a Next.js (App Router) app deployed to Cloudflare Workers via the OpenNext Cloudflare adapter, using Cloudflare D1 (SQLite) as its database through Prisma's D1 driver adapter. Auth is NextAuth v4 (`src/lib/auth.ts`) with the Google provider, database session strategy, and the Prisma adapter.

**Prisma + D1 has real bundling gotchas — do not "fix" these back to what looks more normal:**
- `prisma/schema.prisma`'s generator block must be exactly `previewFeatures = ["driverAdapters"]`. Do **not** add `engineType = "client"` or `runtime = "workerd"` — that switches Prisma to its newer engine-less mode, whose wasm dynamic-import gets mis-bundled by OpenNext's esbuild pass into a `fs.readFileSync` call that has nothing to read on Workers (confirmed by direct testing; this is an open upstream gap as of Prisma 6.19 / `@opennextjs/cloudflare` 1.20, tracked in `opennextjs-cloudflare#471`).
- `next.config.ts` must keep `serverExternalPackages: ["@prisma/client", ".prisma/client"]`. Without it, Next's own bundler inlines those packages and breaks the same wasm loading in a different way.
- `src/lib/prisma.ts` exports `getPrisma()`, an **async function**, not a module-level singleton — the D1 binding (`env.DB`) only exists within a request's Cloudflare context (`getCloudflareContext()`), so every server component and route handler calls `const prisma = await getPrisma()` itself. Same pattern for auth: `src/lib/auth.ts` exports `getAuthOptions()` (async), not a static `authOptions` object, because the adapter needs a fresh Prisma client per request.
- D1 doesn't support Prisma's interactive `$transaction(async tx => ...)` form, only the sequential/batched array form. `awardPoints()` in `src/lib/points.ts` is the reference for this.
- SQLite has no native array type — `Project.tags` is `Json`, not `String[]`, and is cast at the server-component boundary before being passed to client components.
- Wrangler's generated `cloudflare-env.d.ts` (from `npm run cf-typegen`) redefines global `Request`/`Response` types project-wide, making `.json()` return `unknown` instead of `any` — this hits client components too, not just server code. Cast explicitly at each call site rather than fighting the global type.
- Local dev (`npm run dev`) emulates D1 through `initOpenNextCloudflareForDev()` in `next.config.ts`; that's why `next dev` alone (no wrangler) still has working D1 access. `npm run preview` is the higher-fidelity check since it runs the actual bundled Worker under real workerd.

**Project membership is many-to-many, not owner-based, and roles are functional, not hierarchical.** A `Project` has no single owner column — participation goes through the `ProjectMember` join table (`prisma/schema.prisma`), and `role` is one of `OWNER`, `DEVELOPER`, `TESTER`, `DESIGNER`, `DOMAIN_EXPERT`, `PROJECT_MANAGER`, `BUSINESS_MANAGER`, `OTHER` (labels and the joinable subset live in `src/lib/roles.ts` — the single source of truth used by the create-project form, the join API, and every display; there is no `PAYMENT_INTEGRATOR` anymore, it was replaced by PM/business roles). Anywhere you need to check "is this user allowed to do X on this project" (accept a suggestion, close it, post an update), check specifically for `role === "OWNER"` — the other roles are peers, not lesser permissions. Multiple owners are structurally possible even though the current UI only ever creates one at project-creation time. `ProjectMember.expertise` is a free-text, always-optional companion to `role` ("全端工程師,8年經驗") — filled in by the proposer at creation or any contributor at join time; don't try to make it structured or required.

**A project can point at something that already exists.** `Project.websiteUrl` is optional and for the common case where VibeHub is where an already-shipped side project asks for help, not a pre-build proposal — render it as an outbound link on both `/projects` (a small 🔗 next to the title) and `/projects/[id]` (a full link under the description). Don't confuse this with `neededRoles`/`tags`; a project can have a live site and still be actively recruiting.

**Recruiting is g0v Jothon-style: the proposer declares what's needed, people self-select to fill it.** `Project.neededRoles` (`Json`, array of `ProjectRole` strings) is set at creation time via checkboxes on `/projects/new`. A role counts as "filled" the moment any member holds it — there's no quota (asking for 2 testers doesn't block a 3rd from joining as tester); it's a visible checklist, not a hard gate. This renders in two places: `/projects/[id]` shows a `招募中` section with ✅/🔲 per needed role, and `/projects` list cards show `缺 <role>` badges only for roles that are needed but not yet filled — computed the same way (`neededRoles` minus the set of roles present in `members`) in both places, so if that logic changes, update both `src/app/projects/page.tsx` and `src/app/projects/[id]/project-detail.tsx`.

**Suggestion discussion is open, not owner-only.** Any signed-in user — not just the project owner or members — can comment on a suggestion via `Comment` (`src/app/api/suggestions/[id]/comments/route.ts`), modeling the real pattern this was built from: a domain expert flags a legal/business detail, other contributors and the owner reply in the same thread. Don't gate commenting behind membership. Separately, `ProjectUpdate` is the owner broadcasting progress to the whole project (e.g. "fixed the three things you reported") — it's project-scoped and owner-only, not a reply to any one suggestion. Keep these two concepts distinct rather than merging them.

**Points are an append-only ledger, never a mutable counter.** `User.pointsBalance` is a cached total that must only ever be changed by `awardPoints()` in `src/lib/points.ts`. Do not write to `pointsBalance` directly from anywhere else. Any new way to earn/spend points should add a new `LedgerReason` enum value and go through `awardPoints`.

**Referrals are staged, not a flat invite bonus.** `src/lib/referrals.ts` pays the *inviter* three separate awards — signup, invitee's first accepted suggestion, invitee's first closed owned project — each gated by checking the ledger for an existing entry with that `(reason, refType: "Referral", refId: inviteeId)` before awarding, so re-triggering the check (e.g. a second suggestion getting accepted) never double-pays. New "first X" milestones should follow this same idempotency-via-ledger-lookup pattern rather than adding boolean flags to `User`.

**Route structure**: `src/app/api/<resource>/route.ts` for collection endpoints, `src/app/api/<resource>/[id]/<action>/route.ts` for actions scoped to one resource (e.g. `projects/[id]/join`, `suggestions/[id]/accept`). Route handlers do their own `getServerSession` + membership/role checks inline rather than through shared middleware.

Suggestion acceptance (`src/app/api/suggestions/[id]/accept/route.ts`) is the reference flow for "action that must be owner-gated, awards points, and can trigger a referral milestone."

**`/` is deliberately fully static — do not add a DB call to it.** No `dynamic = "force-dynamic"`, no `getPrisma()` call. Cloudflare serves prerendered pages from Workers' static-assets layer with long edge caching, so keeping the landing page free of per-request data is what makes it fast; live data (like project counts) belongs on `/projects`, which is already `force-dynamic` for correctness reasons (see the comment in that file). If a future landing-page redesign wants live stats, prefer client-side fetching after the static shell loads over making the page itself dynamic again.

**Admin access (`/sys/*`) is a DB column, not an env-var allowlist.** `User.isAdmin` is checked once, centrally, by `getAdminUserId()` in `src/lib/admin.ts` — `src/app/sys/layout.tsx` calls it and redirects to `/` for anyone who isn't an admin, so individual `/sys/*` pages don't re-check. All mutating `/api/sys/*` routes call `getAdminUserId()` themselves too (the layout guard only protects page rendering, not the API routes a browser could hit directly). Being a DB column, not a hardcoded list, is what lets an admin grant admin to someone else from `/sys/users` — don't reintroduce an env-var/config-file allowlist alongside it. The one safety rail: `/api/sys/users/[id]/admin` refuses to demote the last remaining admin. Admin-triggered project actions (force-close, delete) reuse the same underlying effects as the owner-facing ones — e.g. `/api/sys/projects/[id]/close` still runs `checkFirstProjectReferral`, matching `/api/projects/[id]/close` — so an admin acting on someone's behalf doesn't silently skip milestones that would have fired otherwise.

**Mentor status is computed, not stored.** `isMentor()` in `src/lib/mentor.ts` is a pure function of `User.pointsBalance` against `MENTOR_THRESHOLD_POINTS` (200) — there is no `isMentor` column. This is deliberate: it's the smallest possible slice of a much larger planned Learn/Community/Teach system (courses, study groups, an actual "who can teach what" model), scoped down to just recognition on the Vibe Passport (`/u/[id]`) and `/me`, so the "accumulate reputation → become a Mentor" loop can be validated before building the rest. If courses/study-groups get built later, they should read this same threshold/function rather than introduce a separate, parallel notion of teaching eligibility — and at that point `isMentor` may need to become a stored, explicitly-granted status instead of a pure points threshold (e.g. if teaching should require more than just points), but that's a deliberate future upgrade, not an oversight.

## Current scope

Implemented: static landing page (`/`) with a search box into `/projects`, project board with keyword search (`/projects?q=`) and role-recruiting badges, multi-participant projects with functional roles and declared `neededRoles`, suggestions with open comment threads and owner-gated acceptance, owner progress-update broadcasts, points ledger (including a one-time `WELCOME_BONUS` on first Google sign-in via NextAuth's `createUser` event), staged referral rewards with shareable invite links (`/invite/[userId]`), a public leaderboard (`/leaderboard`) ranking by both points and referrals, project close (triggers the "first project" referral milestone), Vibe Passport public profile pages (`/u/[id]`) with a computed Mentor badge, and an admin backend (`/sys`: dashboard, user management with manual point adjustment and admin-granting, project moderation, suggestion/comment moderation).

Not yet implemented: the rest of the Learn/Community/Teach vision (structured courses, study groups, an actual course-authoring/enrollment system), test-task coordination, competitions/challenges. When adding these, prefer extending the existing `ProjectMember`/ledger/Mentor patterns over introducing parallel membership, balance, or reputation mechanisms.
